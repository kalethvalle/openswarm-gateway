# Validación de OpenSwarm v0.2

Fecha: 2026-10-02. Entorno: macOS Apple Silicon, Node.js 22.23, SQLite y Docker Desktop. Las pruebas usan el perfil gratuito configurado; no se activaron proveedores de pago. Este informe distingue contratos comprobados de disponibilidad y calidad generativa.

## Resumen

| Comprobación | Resultado | Alcance |
| --- | --- | --- |
| `npm run verify` | Aprobado | Especificaciones, TypeScript, 84 pruebas offline y compilación |
| SDK: saludo SSE y herramienta echo | Aprobado | Inferencia real y continuación de una herramienta ejecutada por el cliente |
| OpenClaw con contexto habitual | Bloqueado | Contexto mayor que la cuota configurada de Groq; cuota gratuita de OpenRouter agotada |
| OpenClaw aislado con archivos y exec | Incompleto | Una llamada exec sin fallo creó los dos archivos; la continuación excedió la capacidad configurada |
| Docker: Gateway + Laya + saludo | Aprobado | Imágenes construidas, servicios listos e inferencia real; checkpoint público ya descargado |
| Calidad del enrutamiento Laya | Medida, pendiente de calibración | 13 aciertos entre 15 decisiones aceptadas sobre 60 casos |
| Comparación de generación de código | Piloto aprobado | Una tarea por estrategia; no demuestra superioridad de colaboración |

Las pruebas offline simulan proveedores y cubren fallos y persistencia. No prueban que un modelo gratuito esté disponible durante todo un día.

## Contratos y regresiones

`npm run verify` ejecuta `spec:check`, `typecheck`, `test` y `build`.

- Runtime: estimación de tokens, presupuestos y cancelaciones sin bloquear turnos futuros.
- Registro: alias por proveedor, elegibilidad gratuita, catálogo degradado y parámetros opcionales de herramientas.
- Cuotas: reservas atómicas, límites compartidos, fallbacks, cooldown por cuenta/modelo y persistencia.
- Laya: respuestas tipadas, abstención, indisponibilidad, entrada acotada y fallback generativo.
- Colaboración: consultas anidadas, fuentes canónicas, ciclos, límites y respuesta integrada sin controles privados.
- Integración: replay, migración v1/v2, portabilidad entre proveedores y reinicio con un especialista esperando una herramienta externa.

La evidencia por requisito figura en `specs/*/validation.md`. Los logs completos y resultados privados permanecen en `data/` o archivos temporales, excluidos de Git.

## Pruebas reales de OpenClaw

### Contexto habitual

`RUN_LIVE_SMOKE=1 npm run smoke:normal` usa el Gateway de OpenClaw existente, sin entregar mensajes a canales externos. El saludo llevaba aproximadamente 46 KB de entrada y 13.356 tokens estimados, antes de reservar la salida. El perfil Groq admite 8.000 TPM por modelo: la petición completa no cabe. OpenRouter devolvió HTTP 429 por cuota de cuenta.

El cliente reintentó y la prueba terminó por su límite de tiempo. No se descartaron instrucciones para hacerla pasar. No se debe repetir continuamente mientras la cuota siga agotada.

### Herramientas en carpeta aislada

`RUN_LIVE_SMOKE=1 npm run smoke:openclaw` logró una llamada `exec`, sin fallo reportado por OpenClaw, y creó `tasks.mjs` y `tasks.test.mjs`. La siguiente llamada necesitaba 6.834 tokens estimados de entrada + 2.048 de salida, superando 8.000 TPM. El fallback OpenRouter también confirmó su cuota agotada. No hubo respuesta final integrada ni revisión independiente comprobada: la prueba está incompleta.

La configuración aislada desactiva búsqueda de memoria para evitar invocar un proveedor de embeddings heredado, además de desactivar memory flush. Este ajuste no modifica la configuración personal de OpenClaw.

### SDK con contexto pequeño

`RUN_LIVE_SMOKE=1 npm run smoke` completó saludo SSE, llamada a `echo`, devolución del resultado y respuesta final. Confirma el ciclo real básico de herramientas con el Gateway v2.

### Cómo continuar

1. Consultar las cuotas efectivas de la cuenta y ajustar el YAML a esos valores, sin aumentarlos artificialmente.
2. Para contextos grandes, habilitar un modelo local con capacidad suficiente o esperar disponibilidad de un proveedor gratuito compatible.
3. Para una prueba pequeña, usar un perfil aislado de OpenClaw con pocas herramientas. Ajustar la reserva de salida a la tarea puede ayudar; no reduce el contexto obligatorio ni garantiza disponibilidad.
4. Repetir la prueba habitual y la de herramientas cuando exista capacidad y registrar el resultado en SPEC-006.

## Evaluación de Laya

Se separaron 20 casos de desarrollo y 60 de evaluación (40 español, 20 inglés). Producción y evaluación comparten `decisionInput`. Umbral provisional: 0.95.

| Conjunto | Casos | Aceptados | Aciertos aceptados | Cobertura | Precisión entre aceptados |
| --- | ---: | ---: | ---: | ---: | ---: |
| Desarrollo | 20 | 5 | 5 | 25% | 100% |
| Evaluación separada | 60 | 15 | 13 | 25% | 86,7% |

Los otros 45 casos de evaluación se abstuvieron y requieren fallback generativo en producción. Hubo dos errores incluso entre las decisiones aceptadas: confianza 0.95 no equivale a precisión 95%. Esta evaluación mide la especialidad inicial; no valida todavía la precisión de relevancia de fuentes ni clasificación de aportaciones entre modelos.

La revisión 2 de SPEC-004 eliminó una segunda clasificación inicial redundante después de que la versión anterior aceptara 0/20 casos de desarrollo. Los casos separados no se utilizaron para ajustar ese cambio. Refinamientos futuros deben añadir un nuevo conjunto separado para evitar sobreajuste a estos resultados.

Reproducción, con Laya iniciado:

```sh
npm run eval:routing -- --development
npm run eval:routing
```

## Piloto de generación de código

Se ejecutó la tarea `sum` del conjunto de 20 funciones con los tres modos. El código generado pasó las assertions dentro de Docker sin red.

| Estrategia | Tareas aprobadas | Llamadas | Tokens contabilizados | Tiempo total |
| --- | ---: | ---: | ---: | ---: |
| Modelo único | 1/1 | 1 | 83 | 5.329 ms |
| Secuencia | 1/1 | 2 | 1.017 | 2.025 ms |
| Colaboración | 1/1 | 3 | 1.540 | 2.697 ms |

Los tiempos incluyen preparación/verificación Docker, con calentamiento en la primera ejecución; no sirven para comparar latencia de inferencia. En esta tarea el modelo único consumió menos llamadas y tokens. Una tarea no permite concluir mejora de calidad, ahorro ni fiabilidad diaria. El benchmark completo queda pendiente.

Huella del dataset y configuración de este piloto: `3cebae0cdc55ceff3ce64dddb4cd0b2bd6ad5756c3ff0fd8a81d4e1d0f64254f`.

```sh
RUN_LIVE_BENCHMARK=1 BENCHMARK_MAX_RUNS=3 npm run benchmark
```

El comando reanuda tareas pendientes según su huella y conserva intentos bloqueados o fallidos. Aumentar `BENCHMARK_MAX_RUNS` consume más cuota. Deben completarse las 20 tareas por modo y controlar calentamiento, orden y repeticiones antes de comparar rendimiento.

## Docker y distribución

```sh
RUN_DOCKER_SMOKE=1 DOCKER_HF_CACHE=/ruta/al/cache/huggingface/hub npm run smoke:docker
```

La prueba construye las dos imágenes, crea contenedores temporales, espera a Laya y Gateway, realiza una inferencia y elimina sus contenedores/red. Usa puertos 3001/8002 para no interferir con el desarrollo local. Se verificó con la caché pública del checkpoint; una descarga inicial desde una máquina vacía no fue comprobada.

El repositorio contiene licencia MIT y CI sin secretos. El workflow de GitHub está definido pero no se ejecutó remotamente. No se publicó el repositorio ni una imagen.
